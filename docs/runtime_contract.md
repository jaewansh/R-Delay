# R-Delay 실행 시제품 v0.2 — 구현 계약

이 문서는 실제 서비스 소스의 범위를 설명한다. v0.1 제출 Word/PDF는 덮어쓰지 않는다. 모델이 현실에서 유효하다는 입증과 합성 구현 검사는 다르다. 실제 검사 결과는 `artifacts/runtime/validation_summary.json`, 브라우저 검사는 `artifacts/runtime/browser_check.json`에서 확인한다. 파일이 없으면 검사 완료로 간주하지 않는다.

## 기존 설계에서 유지한 것

`engine/sis.py`는 dI_i/dt = beta_i(1-I_i/N_i) sum_j C_ij I_j - gamma_i I_i를 사용한다. 비율 변환에서 N_j/N_i를 유지한다. C_ij는 j→i, 전파·회복률·M은 /h, tau0=1h, C와 kappa는 무차원이다. 구현은 해상 P→육상 L의 두 거점, 같은 의미의 일정 작업 100개씩이다. SIS는 선박 수의 보존 이동식이 아니다. R_d는 각 입자의 frozen-state 행렬 스펙트럼 반지름이며 화물 실패확률이 아니다.

## 실행 경로

과거 에피소드의 합성 관측 → 상수 회복률 추정 → 새 에피소드의 SIS·로그-OU 예측 → 10:00 관측 1회 필터링 → 그 이후 경로 → 선석 Kolmogorov 전진방정식 → 대상 선박의 대기·서비스 → 화물 준비 → 육상 처리 → 원래 마감 위험·실행조건·표본 비교비용 → 웹.

Python이 모든 계산을 수행한다. 브라우저 JavaScript에는 별도의 위험 계산 모델이나 하드코딩된 결과표가 없다.

## 새로운 합성 사례 B의 고정 조건

- 가상 날짜 2026-10-21, 기준시각08:00, 판단시각10:00, 대상 선박 도착11:00, 원래 수령지 마감16:00, 계산기간 종료 다음날00:00.
- 이것은 과거 다섯 상태/13:15 예제와 다른 선석 시나리오다. 이전35.81% 등을 기대값으로 강제하지 않는다. 16:00 마감은 후보 사이에서 절대 바꾸지 않는다.
- 과거08~10시로 추정한 gamma_L을 별도 새 사례에 적용한다. 같은 화물의 과거 판단을 미래 관측으로 소급 개선하지 않는다.
- 10:00 시스템 내 선박 수2를 직접 안다고 가정한다. SIS 지연 작업 수와 다르다. 이 시점의 대기열 분포는 알려진 관측에 조건부로 초기화하므로 그 이전 대기열 경로를 보존·필터링했다고 주장하지 않는다.
- 신규 사건 관측은08~10시 SIS 생성항 적분에 조건부인 음이항, 현재 표본 관측은 베타-이항. 후자는 bounded counts를 위한 추가 설계다. 관측이 없으면 예측 가중치를 유지한다.
- 정확히10:00에 발생·이용 가능한 관측1회만 지원한다. 다른 시각/늦게 수신한 관측은 명시적으로 거부한다. observations API는 같은 시각의 관측을 바꾸고 같은 시드에서 다시 계산하며 임의 다시간 실시간 스트리밍이 아니다.

## 구현 세부와 추가 연결 가정

1. 로그-OU는 평균회귀 theta=.6/h와 지정sigma로 정규 전이식을 사용한다. beta=base_beta*exp(z), 현재 장기 로그평균0이다. beta_base는 산술평균 전파율이라고 부르지 않는다. SIS는 구간 중간 로그계수를 고정한 RK4이며 시간오차 검사는 OU와 별개다.
2. 입자 가중치는 log-likelihood/logsumexp로 갱신한다. ESS<P/2이면 systematic resampling. 요약은 재표본추출 전 가중 분포에서 계산한다. 미래 경로는 갱신한 조상 상태에서 시작한다. 이전 시각 요약을 사후 평활 결과로 덮어쓰지 않는다.
3. 선석은 선입선출·동질 서버2개, 배경 도착률0.4척/h, 서비스 위험률 mu=1.5 exp(-0.8 x_P)*open 이다. mu와 SIS gamma는 다른 양이다. 1분 구간 내 고정률의 전진방정식을 uniformization으로 풀며, 상태0..K와 별도 흡수 넘침상태를 사용한다. 시간격자 밖 실제 연속률 해법과는 수치근사 차이가 있다.
4. 선박 도착 직전 분포에서 시스템 내 선박 수를 뽑는다. n>=m이면 서비스 시작까지 n-m+1번 완료가 필요하고, 공통 서비스 운영시간에서 Gamma(n-m+1,1/m) 작업을 사용한다. 본인 서비스는 Exp(1). 이는 동질 시간가변 지수 서버 가정에서만 성립한다. 나중에 도착하는 선박은 선입선출의 대상 선박을 추월하지 않는다. 대상 선박은 딱 한 번 삽입한다.
5. 준비시각=max(선박 작업 완료+15분, 문서준비11:15). 전체 선박 작업 이후 해당 화물의 준비가 끝난다는 축소 가정으로서 컨테이너별 실측 하역 순서는 없다. 이미 준비시각에 포함한 선석 대기를 다시 더하지 않는다.
6. 육상 누적 작업량 Q_L=integral((1-0.8*x_L)/0.5)dt. max(준비,차량도착)부터 한 단위 작업량을 채운 뒤 반출한다. 도로90분 추가. 한 건의 배차가 배경 SIS를 바꾸지 않는다.
7. 후보 간 동일 입자·선박표본·원래 마감을 사용한다. 예약·차량·승인 미확인, 승인20분+안전10분+접근30분 부족 후보는 확정 추천에서 제외한다.
8. 준비대기30,000원/h, 실패600,000원/건, 후보별 변경비용은 합성값이다. 기본운임·실제 부담자·절감 실적은 미확인이다.
9. 계산기간 내 준비되지 않은 표본은 마지막 시각의 완료로 처리하지 않는다. 마감보다 늦은 계산기간까지 미완료인 경로는 마감실패로 판정할 수 있지만, 대기비용 전체는 미확정이다. 비용 하한만 표시하고 추천을 보류한다. 넘침 표본의 위험은 하한/상한으로 분리하며 넘침질량이1e-6보다 크면 추천을 보류한다.
10. 10~90% 입자 분위수와 조건부 Monte Carlo 위험은 현장 신뢰구간이 아니다. 재표본추출 계보에 따른 표본 의존성을 무시한 이항 신뢰구간을 제공하지 않는다. 모수 추정오차의 전체 사후분포는 아직 없다.

## API와 운영상 제한

`POST /api/v1/runs`, `GET /api/v1/runs/{id}`, `POST /api/v1/runs/{id}/observations`, `GET /api/v1/runs/{id}/artifacts`, `POST /api/v1/calibrations`, `GET /health`를 제공한다. 입력은 Pydantic에서 범위·시각·알려지지 않은 필드를 검사한다. 최초 명세의 비동기 작업큐는 아직 없으며 로컬 시제품은 한 번에 한 계산만 실행한다. 최근32개 실행을 메모리에 보관한다. 서버 재시작 시 사라지므로 JSON 다운로드가 필요하다.

외부 항만 API·실제 자료 업로드·인증·공개 운영·실제 예약 변경은 없다. API와 UI는 127.0.0.1에서만 실행하는 것을 기본으로 한다. 공개 서비스에 필요한 인증·rate limit·영속 저장·보안 점검은 별도다.

## 이번에 구현하지 않은 기능 (이번 대회 목표에서 제외한 뜻은 아님)

외생변수에서 beta/gamma를 학습하는 모델, 일반 다거점 UI, 늦은 관측 재처리, 다시간 스트리밍 필터, 대기열 관측을 사용하는 공동 갱신, 실측 연결행렬 추정, 실제 고객 파일럿, 공공 인터넷 배포. 일정·성능·정확도 완료를 주장하지 않는다.
